# 35. 구버전(goteacher.xyz) → 고티처(티로드) DB 이관 계획 (개정 2026-11-09)

근거 데이터는 `34_legacy_db_analysis.md`. 1차 초안(같은 날)은 "구글 로그인만·일정 본문 없음·무료 플랜" 전제였다. 사용자 지시(2026-11-09)로 전제가 바뀌어 다시 썼다.
- 아이디·비밀번호 로그인 유지 + 신규 가입도 아이디로 → 작업 **P1**
- 일정에 본문·첨부·댓글 → 작업 **P2**
- 이관 학교는 모두 유료 플랜 → 이관 도구 **P3**

작업 정의와 리드 결정은 `32_tasks_r2.md` P절에 있다.

## 0. 한 줄 요약

구 회원 계정을 **같은 아이디·같은 비밀번호(구 해시 그대로)**로 옮긴다. 그래서 잇기 화면 없이 출시 날부터 평소처럼 로그인한다. 이관 학교는 학교 공간(유료 플랜)으로 만들고, 회원을 소속·반과 함께 넣는다. 일정은 범위(학교 전체·소속·나)에 맞춰 본문·첨부·댓글까지 옮기고, 게시판은 학교 게시판으로 옮긴다. 이관 도구는 다시 돌려도 결과가 같아야 한다. 스테이징 리허설 뒤 출시 주말에 구 사이트를 쓰기 중지하고 최종본을 옮긴다.

## 2. 대응표(구 → 티로드)

| 구버전 | 티로드 | 규칙 |
|---|---|---|
| `g5_member`(탈퇴·차단 제외 2,890) | `auth.User` | username=`mb_id`(입력 그대로, 로그인은 대소문자 무시), password=`g5pbkdf2$<mb_password>`, first_name=`mb_name`, email=비움(구 메일은 확인 안 된 값이라 저장하지 않음), date_joined=`mb_datetime`, last_login=`mb_today_login` |
| `school`(이관 학교) | `spaces.School(neis_atpt=code_sido, neis_code=id, name, plan=school, paid_until=D6')` | 학교마다 `Space(kind=school, grade=0)` 하나 |
| 이관 학교의 가입 회원(`mb_5='1'`) | `spaces.Member(space, user, name, cls, group, position)` | 소속 규칙 2-1 |
| `g5_write_go_admin` | `Member.is_manager=True` | 학교에 관리자가 없으면 그 학교 첫 가입자 |
| `g5_write_goteacher`(일정) | `today.Event` + P2의 본문·첨부·댓글 | 범위 규칙 2-2, 복무는 D4 |
| `g5_board_file`(bo_table=goteacher) | P2의 일정 첨부 | 원래 이름 `bf_source`. 형식 검사를 통과해야 넣고, 실패는 보고서에 남김 |
| 일정 댓글(`wr_is_comment=1`) | P2의 일정 댓글 | 쓴 사람 자리(없으면 이름 글자만), 작성일 보존. 댓글 첨부는 버림 |
| `g5_write_free_school`(게시판) | `notices.Notice` + `NoticeVersion`(본문) + `NoticeFile` | by=작성자 자리, by_name·group=그 자리 값, audience=전체, 작성일 보존. 공지(`wr_1=1`)는 표시 없음, 댓글 5건은 버림 |

- 본문은 HTML을 평문으로 바꾼다. `<br>`·`</p>`·`</tr>`는 줄바꿈, 표 칸은 탭, 엔티티는 풀어 쓴다. 본문 속 그림(2026학년도 34건)은 `[그림]` 자리표시로 남긴다.
- created_at(`wr_datetime`)은 `auto_now_add` 때문에 넣은 뒤 `update()`로 덮어쓴다.
- 첨부 실물 판별(P4 판별기로 M1 리허설본 2,012개를 돌림, 11/9): **받음 1,944(96.6%)**, 받지 않는 형식 60(zip 42·mp3 4·txt 4·ai 2·exe 2·xlsm 2·pptm 1·ttf 1·jfif 1·hwtx 1), 매크로 든 xls 4(거부), 이름은 hwp인데 내용은 hwpx 3, 판별 안 되는 xls 1. 이관 규칙: 한글끼리(hwp↔hwpx)는 판별한 형식으로 확장자를 고쳐 넣고, `jfif`는 jpg로 받는다. 나머지는 버리고 보고서에 이름·까닭을 남긴다. 디스크에 없는 5개·`bf_file` 빈 14행도 보고만 한다.
- 한도 대조(운영 DB, 11/9): 일정당 첨부 최대 2개(한도 5), 20MB 넘는 파일 0, 댓글 1천 자 초과 2건. 본문은 **HTML 원문 기준 1만 자 초과가 691건**이다. 평문으로 바꾼 뒤 다시 재고, 넘는 것은 이관 도구가 화면 한도를 거치지 않고 그대로 넣는다(모델 칸은 길이 제한 없음). 그런 일정을 화면에서 고치면 1만 자 안내가 뜨는 것은 받아들인다.

### 2-1. 그룹 → 소속(Member.group / cls / position)

| 구 그룹 이름 | 소속 | cls / position |
|---|---|---|
| 1~6학년 | g1~g6 | `mb_4`가 `N반`이면 cls=`학년-N`, `전담`이면 `학년-전담`. 그 밖의 글자는 cls=`학년-전담`, position=그 글자 |
| 교무실·관리자·교장실·교무부·비교과 | office | cls=`교무실`, position=`mb_4`(교장·교감·교무·교사…, `교직원`이면 비움) |
| 행정실 | admin | cls=`행정실`, position=`mb_4` |
| 급식소·급식실·영양사실 | meal | cls=`급식소`, position=`mb_4` |
| 그 밖(병설유치원·기관·교육공무직·보건실·특수학급·늘봄/돌봄·위클래스·도서실…) | support | cls=`기타/지원`, position=구 그룹 이름(+` · mb_4`), 40자 안 |
| 전출·휴가&휴직 | — | 학교 자리를 만들지 않는다(계정은 있음) |
| 그룹 없음·다른 학교 그룹 | support | position 비움, 보고서에 표시 |

- 같은 학교·같은 cls·같은 이름이 둘이면 두 번째부터 이름 뒤에 `(2)`를 붙이고 보고서에 남긴다(반·이름 겹침 금지 규칙 때문).
- `SCHOOL_SEATS=300`: 이관 학교 중 최대는 가입 101명이라 걸리지 않는다.

| wr_4 | scope | 비고 |

- by=작성자 자리(없으면 비움). 학교 공간이므로 by가 비면 관리자만 고칠 수 있다.
- 색(wr_9)·완료(wr_5)·공지(wr_6)는 티로드에 없어 버린다.
- "다른 채널로 복사"로 생긴 중복(749묶음)은 바뀐 범위가 같아지면(예: 0과 1) 하나만 넣는다. 첨부·댓글은 남기는 쪽으로 모은다.
- 제목 200자, 끝 날짜는 `wr_2 > wr_1`일 때만 넣는다.

### 4-1. 이관 도구 요건

- 덤프를 읽어 넣는 Django 관리 명령 하나로 한다. MySQL 덤프는 로컬 MySQL 컨테이너에 올려 읽거나, M1에서 표별 JSON으로 받는다(쉬운 쪽).

- 이미 있는 username과 겹치면(전환 전에 티로드에서 같은 아이디로 가입한 경우) 멈추고 보고한다. 자동으로 덮어쓰지 않는다.

- 학교별 대조 보고서(CSV): 구 건수 / 넣은 건수 / 버린 건수와 까닭.

## 5. 검증(끝났다는 기준)

1. 학교별 대조: 범위별 일정·복무·댓글·첨부·게시글·자리 수가 보고서의 "넣음 + 버림(까닭별)"과 정확히 맞는다.
2. 격리: 모든 Event·Attendance·Notice·Member의 공간이 구 `wr_3`/`mb_1` 학교와 같다.
3. 범위: `me` 일정과 그 본문·첨부·댓글은 작성자 외(관리자 포함)에게 안 보인다. 소속 일정은 그 소속에게만 보인다.
4. 로그인: 이관 계정 표본 몇 개는 운영자가 본인 동의를 받아 확인한다. 그 밖에 해셔 단위 테스트, 첫 로그인 뒤 새 해시로 바뀌는지 확인한다.
5. 표본: 학교마다 무작위 20건을 구 화면과 티로드 화면(1536×750)에서 날짜·제목·범위·본문·첨부 이름이 같은지 본다.
6. 첨부: SHA-256이 원본과 같고 내려받기가 된다.
7. 재실행: 같은 덤프로 두 번 돌려도 건수가 늘지 않고, 증분 덤프는 새것만 더한다.
8. 시간: 전체 적재가 전환 날 작업 시간 안(목표 30분, 첨부 복사 별도)에 끝난다.

## 6. 전환 순서(12/12 금 저녁 ~ 12/14)

1. 구 사이트에 쓰기 중지 공지 → 그누보드 쓰기 막기(맥에서 고쳐 배포 스크립트로)
2. 최종 덤프·첨부(M1) → 맥
3. 티로드 운영 DB 백업 → `[시연]` 데이터 삭제 → `import_legacy` → 보고서 확인
4. 5절 1~3을 빠르게 재확인
5. Traefik: `goteacher.xyz` → 티로드, 구 컨테이너 → `old.goteacher.xyz`(읽기 전용). 구글 동의 화면 프로덕션 게시
6. 첫 주는 매일 로그인 실패·문의를 확인한다. 비밀번호 분실은 학교 관리자가 임시 비밀번호를 발급한다(P1)

되돌리기: 5번 전이면 구 사이트 쓰기만 다시 연다. 5번 뒤면 라우터를 구 컨테이너로 되돌리고, 그 사이 티로드에 쓴 것은 따로 받아 둔다.

## 7. 개인정보·보안

- 옮기지 않는 것: 전화번호(암호화된 것 포함), 확인 안 된 메일, 학교 PIN, 채널 비밀번호, FCM·세션 토큰, 방문·읽음 기록.
- 구 비밀번호 해시는 PBKDF2-SHA256 1.2만 회로 지금 기준에 약하다. 첫 로그인 때 바로 새 해시로 바뀐다. 2027-03까지 한 번도 로그인하지 않은 이관 계정은 비밀번호를 쓸 수 없게 하고(관리자 임시 발급으로만 복구), 이 사실을 안내문에 넣는다.
- 덤프에는 이름·비밀번호 해시가 있다. 저장소 밖에만 두고 커밋하지 않는다. 전환 30일 뒤 지운다.
- 처리방침: 아이디·비밀번호(해시) 수집(P1), "구 고티처 회원 정보와 작성한 일정·게시글을 새 고티처로 옮김"을 넣고 구 사이트에 미리 알린다(사람 할 일). 같은 운영자·같은 서비스의 개편이라 고지로 충분한지 운영자가 확인한다.
